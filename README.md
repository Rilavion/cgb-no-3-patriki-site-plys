# Учёт поставок ЗМХ / МС

Компактная система оперативного учёта сотрудников организаций, присутствующих на поставках ЗМХ и МС. Приложение работает в браузере, хранит каждую поставку отдельным документом Cloud Firestore, получает изменения через `onSnapshot()` и публикуется как статический сайт на GitHub Pages.

## Возможности

- быстрые цветные счётчики `− / ручной ввод / +` с эмодзи для одиннадцати организаций;
- получатель из фиксированного списка организаций, Правительства, Суда, Прокуратуры и СК;
- результат «Довезли / Не довезли», дата и время в московском часовом поясе;
- количество матавозок и необязательный трёхпозиционный статус сопровождения;
- локальный автосохраняемый черновик текущей формы, кнопка «Сейчас» и отмена случайного обнуления;
- итоговое подтверждение перед сохранением;
- анимированное сохранение с грузовиком и отдельное состояние успешной записи;
- realtime-история, поиск, фильтры, просмотр, редактирование, дублирование и защищённое подтверждением удаление;
- транзакционное редактирование с номером ревизии: устаревший клиент не перезапишет более свежую версию;
- статистика по периоду, месту, организации, получателю и результату доставки;
- динамика, donut-диаграмма, рейтинг, сравнение ЗМХ/МС и таблица показателей;
- отдельная Canvas PNG-карточка 1600×900 для Discord, надёжное копирование в буфер или скачивание с автоматическим fallback;
- экспорт CSV и резервной копии JSON;
- адаптивный интерфейс для телефона, планшета и ПК;
- понятные состояния загрузки, ошибки, отсутствия сети и успешных операций.

## Структура Firestore

Коллекция создаётся автоматически при первой успешной записи. Вручную создавать её не нужно.

```text
supplies/{supplyId}
  location: "ZMH" | "MS"
  recipient: string
  status: "DELIVERED" | "NOT_DELIVERED"
  truckCount: int              # количество матавозок, 0–99
  escortStatus: "YES" | "NO" | "UNKNOWN"
  eventAt: Timestamp
  comment: string
  organizations:
    fso: int
    fsb: int                   # отсутствует только у старых записей
    uvd_cao: int
    gibdd: int
    vs_rf: int
    codd: int
    fsvng: int
    fsin: int
    moscow_life: int
    cgb7: int                  # ЦГБ №7; отсутствует только у старых записей
    cgb3: int                  # ЦГБ №3; отсутствует только у старых записей
  total: int
  revision: int
  createdAt: server Timestamp
  updatedAt: server Timestamp
```

`eventAt` — указанная пользователем дата поставки. `recipient` — получатель, которому везлась поставка. `status` хранит результат доставки. `truckCount` хранит количество матавозок, а `escortStatus` — ответ о сопровождении. У старых записей эти два поля автоматически отображаются как `0` и `UNKNOWN`. `createdAt` и `updatedAt` создаются через `serverTimestamp()`, поэтому не зависят от часов устройства. Каждая поставка — отдельный документ; сохранение, изменение и удаление одной записи не перезаписывает остальные.

Старые документы без `recipient` и `status` продолжают читаться: интерфейс показывает для них «Получатель не указан» и «Статус не указан». При редактировании такая запись автоматически переводится на новую схему.

## Подключение Firebase с нуля

### 1. Создать проект

1. Откройте [Firebase Console](https://console.firebase.google.com/).
2. Нажмите **Create a project / Создать проект**.
3. Введите понятное имя, например `supply-control`.
4. Google Analytics для этого приложения не обязателен; его можно отключить.
5. Нажмите **Create project** и дождитесь завершения.

### 2. Зарегистрировать веб-приложение

1. На обзорной странице проекта нажмите значок `</>` (Web).
2. Укажите псевдоним, например `supply-control-web`.
3. Firebase Hosting включать не нужно: сайт будет на GitHub Pages.
4. Нажмите **Register app**.
5. Скопируйте объект `firebaseConfig`. Он похож на этот:

```js
const firebaseConfig = {
  apiKey: "...",
  authDomain: "PROJECT_ID.firebaseapp.com",
  projectId: "PROJECT_ID",
  storageBucket: "PROJECT_ID.firebasestorage.app",
  messagingSenderId: "...",
  appId: "...",
};
```

6. Откройте `lib/firebase.ts`.
7. Замените только значения в уже существующем объекте `firebaseConfig`. Итог должен иметь те же шесть полей и реальные значения из вашей консоли.
8. Не добавляйте кавычки вокруг всего объекта и не меняйте имена полей.

Firebase Web Configuration можно коммитить: `apiKey`, `projectId`, `appId` и остальные значения идентифицируют проект, но сами по себе не дают административных прав. Нельзя публиковать service-account JSON, private key, OAuth client secret, токены Firebase CLI, ключи серверных API и любые секреты Cloud Functions.

### 3. Создать Cloud Firestore

1. В Firebase Console откройте **Build → Firestore Database**.
2. Нажмите **Create database**.
3. Выберите стандартный режим Firestore Native/Standard, если консоль предлагает редакцию.
4. Выберите **Production mode**. Он начнёт с запрета доступа; далее мы сразу установим точные правила.
5. Выберите ближайший к основным пользователям доступный европейский регион. Расположение базы после создания изменить нельзя, поэтому проверьте выбор до подтверждения.
6. Нажмите **Create**.

### 4. Установить Security Rules

1. Откройте **Firestore Database → Rules**.
2. Удалите содержимое редактора.
3. Скопируйте туда файл `firestore.rules` целиком.
4. Нажмите **Publish**.
5. Подождите до минуты и перезагрузите сайт.

Правила разрешают читать, создавать, редактировать и удалять только документы `supplies`. Они проверяют полный набор полей, типы, допустимые места, обязательного получателя длиной до 120 символов, допустимый статус, длину комментария, диапазон каждого счётчика, правильность итога, серверные timestamps и последовательность `revision`. Любые другие коллекции закрыты.

> После перехода с первой версии обязательно повторно опубликуйте обновлённый `firestore.rules`. Пока в Firebase остаются старые Rules, сохранение полей `recipient` и `status` будет отклоняться с `permission-denied`.

## App Check с reCAPTCHA Enterprise

App Check нужно настроить до включения enforcement. Он подтверждает, что запрос пришёл из зарегистрированной веб-версии приложения, и отсеивает значительную часть автоматизированного злоупотребления. Это не вход пользователя и не система ролей; видимой CAPTCHA обычно нет.

### Создание ключа

1. Сначала опубликуйте сайт хотя бы один раз и запишите адрес вида `USERNAME.github.io/REPOSITORY/`.
2. Откройте [Google Cloud Console](https://console.cloud.google.com/) и в верхнем переключателе выберите тот же проект, что в Firebase.
3. Откройте **Security → reCAPTCHA Enterprise** (в некоторых интерфейсах раздел называется Fraud Defense).
4. Если предложено, включите **reCAPTCHA Enterprise API**.
5. Нажмите **Create key**.
6. Тип платформы: **Website**. Тип ключа: score-based, без checkbox challenge.
7. В список доменов добавьте `USERNAME.github.io` без `https://` и без пути `/REPOSITORY`.
8. Если есть собственный домен, добавьте его отдельной строкой.
9. Не добавляйте `localhost` в производственный ключ.
10. Создайте ключ и скопируйте его **site key**. Это публичное значение, не secret key.

### Регистрация в Firebase

1. В Firebase Console откройте **Build/Security → App Check**.
2. На вкладке **Apps** найдите зарегистрированное Web App и нажмите **Register**.
3. Выберите **reCAPTCHA Enterprise**.
4. Вставьте тот же site key.
5. Оставьте TTL 1 час: это разумное начальное значение.
6. Сохраните.
7. В `lib/firebase.ts` замените пустую строку:

```ts
export const appCheckSiteKey = "";
```

на:

```ts
export const appCheckSiteKey = "ВАШ_PUBLIC_SITE_KEY";
```

8. Закоммитьте изменение и дождитесь новой публикации.
9. Откройте опубликованный сайт с нескольких обычных устройств и выполните чтение/создание/изменение.
10. Вернитесь в **App Check → Metrics** и убедитесь, что появляются verified requests.
11. Только после проверки откройте **App Check → APIs/Services → Cloud Firestore** и включите **Enforce**.

После enforcement запросы без действительного App Check token будут блокироваться на уровне Firestore. Для локальной разработки после enforcement используйте официальный App Check debug provider и храните debug token только локально; не добавляйте `localhost` в production key.

### Ограничения безопасности без авторизации

У требования «одна общая ссылка, никакого Auth» есть фундаментальное ограничение: система не знает, кто именно выполняет действие. Поэтому правила не могут отличить сотрудника от постороннего, если запрос прошёл App Check. Публичный Firebase config не является уязвимостью сам по себе, но он позволяет увидеть идентификатор проекта и пытаться обращаться к Firestore напрямую.

App Check уменьшает риск скриптового доступа, но не является полноценной авторизацией и не защищает от решительного злоумышленника, который управляет настоящим браузером на разрешённом домене. При текущих условиях наиболее разумная схема: строгая валидация Rules + App Check enforcement + лимиты бюджета/уведомления + регулярные JSON-резервные копии + отсутствие массового удаления в интерфейсе.

Если нужна существенно более сильная защита без видимого логина, потребуется доверенный серверный слой (Cloud Functions/Cloud Run) с проверкой App Check, rate limiting и дополнительным механизмом допуска. Любой общий пароль или секрет, зашитый во frontend GitHub Pages, не является секретом. Наиболее надёжное различение пользователей требует Firebase Authentication, но оно сознательно не используется в этом проекте по условию задачи.

## Локальный запуск

Нужен Node.js 22 или новее.

```bash
npm install
npm run dev
```

Откройте адрес, показанный в терминале, обычно `http://localhost:3000/`. Без Firebase-конфига интерфейс откроется в демонстрационном состоянии, но сохранение будет заблокировано понятным сообщением. После App Check enforcement для localhost потребуется debug provider.

Проверка производственной сборки:

```bash
npm run build
```

Готовый для публикации набор статических файлов создаётся в `dist/pages`.

## Публикация на GitHub Pages

Проект требует шага сборки, поэтому правильный источник Pages — **GitHub Actions**, а не прямой `/root`. Готовый workflow уже находится в `.github/workflows/deploy-pages.yml` и публикует `dist/pages`. Вариант **Deploy from a branch → /root** подходит только для заранее собранного чистого HTML и для исходников этого React-проекта не сработает.

1. Войдите на [GitHub](https://github.com/) и нажмите **New repository**.
2. Укажите имя, например `supply-control`; выберите public или подходящий вашему тарифу private.
3. Не добавляйте README/.gitignore при создании, потому что они уже есть в проекте.
4. Загрузите всё содержимое папки `supply-control` в корень репозитория, включая скрытые папки `.github` и `.openai`, а также `fon.png`.
5. Убедитесь, что основная ветка называется `main`.
6. Откройте репозиторий → **Settings → Pages**.
7. В **Build and deployment → Source** выберите **GitHub Actions**.
8. Откройте вкладку **Actions**. Workflow `Deploy to GitHub Pages` запустится после push в `main`; при необходимости нажмите **Run workflow**.
9. Дождитесь зелёной отметки у build-and-deploy.
10. Вернитесь в **Settings → Pages** и откройте выданный URL `https://USERNAME.github.io/REPOSITORY/`.
11. Добавьте домен `USERNAME.github.io` в ключ reCAPTCHA Enterprise, как описано выше.
12. После следующей публикации проверьте сайт на этом HTTPS-адресе.

Если вы всё же используете схему «Deploy from a branch», нужно отдельно собирать проект, коммитить содержимое `dist/pages` в корень отдельной ветки `gh-pages`, затем выбрать **Settings → Pages → Deploy from a branch → gh-pages → /(root)**. Не публикуйте корень ветки `main`: там находятся исходники, а не готовый сайт.

## Проверка работы

1. Откройте сайт на двух устройствах или в двух разных браузерах.
2. На первом создайте поставку с несколькими ненулевыми значениями.
3. Укажите получателя и статус; убедитесь, что подтверждение показывает маршрут и правильный итог.
4. После сохранения откройте **История** на втором устройстве: запись должна появиться без обновления страницы.
5. Откройте карточку, измените значение и сохраните. Проверьте новый итог и статистику.
6. В статистике переключите период, место, организацию, получателя и статус; проверьте графики и процент успешных доставок.
7. Нажмите **Скопировать статистику**. В поддерживаемом HTTPS-браузере PNG попадёт в буфер; иначе автоматически скачается.
8. Проверьте CSV в табличном редакторе и JSON в текстовом редакторе.
9. Удалите тестовую запись и подтвердите, что она исчезла на обоих устройствах.
10. После включения App Check проверьте **App Check → Metrics**.

## Резервное копирование

В разделе **Статистика** выберите **Всё время** и нажмите **JSON**. Храните файл отдельно от публичного репозитория, если комментарии или даты считаются служебной информацией. Импорт намеренно не включён: при полностью общих правах массовая запись создаёт лишний риск случайной порчи базы. Восстановление лучше выполнять контролируемым администратором через отдельный одноразовый инструмент или Firebase Console.

Для крупных рабочих баз рассмотрите управляемые резервные копии Firestore/PITR в Google Cloud и заранее проверьте их стоимость и доступность для выбранного плана.

## Диагностика

### «Firebase ещё не подключён»

В `lib/firebase.ts` остались значения `REPLACE_WITH_...`. Скопируйте config именно из **Project settings → General → Your apps → SDK setup and configuration**.

### `permission-denied`

- правила `firestore.rules` не опубликованы или опубликованы в другом проекте;
- приложение использует config другого проекта;
- включён App Check enforcement, но ключ не вставлен, домен не разрешён или сборка ещё старая;
- данные не соответствуют схеме Rules.

### App Check блокирует localhost

Это ожидаемо после enforcement. Используйте официальный debug provider только в локальной конфигурации и зарегистрируйте выданный debug token в Firebase Console. Никогда не коммитьте его.

### Данные не загружаются

Проверьте интернет, DevTools → Console/Network, статус Firebase, правильность `projectId`, наличие Firestore Database и правила. Запрос сортируется только по одному полю `eventAt`, поэтому составной индекс не требуется.

### Сайт открывается, но стили/скрипты дают 404

Убедитесь, что workflow запущен с переменной `GITHUB_REPOSITORY`, а в Pages выбран **GitHub Actions**. `next.config.ts` автоматически добавляет имя репозитория как `basePath` во время GitHub Actions.

### PNG не копируется

Clipboard API для изображений зависит от браузера, HTTPS и разрешения пользователя. Приложение автоматически скачает PNG, если прямое копирование недоступно. Кнопка **Скачать PNG** работает независимо от буфера обмена.

### Сохранение оборвалось при потере сети

Дождитесь восстановления соединения и нажмите сохранение ещё раз. Не полагайтесь на визуальный счётчик как на подтверждение записи — успешное сохранение всегда сопровождается зелёным сообщением и появлением записи в истории.

### Конфликт редактирования

Если другой пользователь успел изменить документ, транзакция отклонит устаревшее сохранение. Закройте окно редактирования, снова откройте актуальную запись и внесите изменения повторно.

## Контроль расходов и эксплуатации

- В Google Cloud Billing настройте бюджет и email-уведомления.
- Периодически смотрите Firestore Usage и App Check Metrics.
- Не включайте неограниченный импорт или массовое удаление на общей странице.
- Не храните в комментариях персональные или секретные сведения: сайт и правила предполагают общую ссылку и общее чтение.
- Перед изменением списка организаций делайте JSON-резервную копию и обновляйте код и Rules одним релизом.
